| ------------------------ | ------------------------------------------- | ---------------- | ---- |
| `sizeof`                 | 运算符，求**整个类型 / 变量占用的总字节大小**                  | 类型所占字节数          | 编译期  |
| `offsetof(type, member)` | 标准宏（`<stddef.h>`），求结构体成员**相对于结构体首地址的偏移字节数** | 成员起始位置距离结构体开头的字节 | 编译期  |
```c
struct S {
    char  a;      /* 1 字节 */

sizeof(struct S)           /* 12 */
offsetof(struct S, b)      /* 4 */
```
>成员加起来 6 字节，`sizeof` 是 12。中间的 6 个字节去哪了？

uint32_t x = 0x12345678;

# 对齐和填充
## 对齐
### 为什么需要对齐
+ Cortex-M3的SRAM访问总线是32位(4字节)宽。CPU读一个uint32_t，硬件的做法是按地址对齐成块来取：地址 `0x20000000`、`0x20000004`、`0x20000008`……每 4 个字节一组，一次总线事务取一组。
+ 在这个前提下：
	+ 读地址`0x20000000`的4字节：一次总线事务，快
	+ 读地址`0x20000002`的4字节：横跨两组`0x20000000`组和`0x20000004`组。Cortex-M3的硬件会自动将它**拆成两次总线事务**拼起来--功能正确，但是多花费1拍。
	+ 但是并非所有硬件愿意处理非对齐访问，Cortex-M0对于非对齐访问就会直接触发HardFault，Cortex-M3/M4也不允许非对齐访问发生在外设寄存器上
>所以“对齐”是总线的**事务粒度**决定的物理约束。C 标准做的事是把它形式化成一套规则，让编译器有据可依地生成快且安全的指令。
### 对齐规则
+ **基本规则**：每个类型有一个**对齐要求**（alignment），`n` 字节的基本类型要求地址是 `n` 的倍数

| 类型                      | 大小  | 对齐要求                                       |
| ----------------------- | --- | ------------------------------------------ |
| char                    | 1   | 1（任何地址都行）                                  |
| short                   | 2   | 2                                          |
| int / long / float / 指针 | 4   | 4                                          |
| double / long long      | 8   | 8（Cortex-M 上硬件按 4 处理，但 ABI[^1] 按 8 对待）<br> |
+ 数组的对齐等于元素的对齐，大小等于元素大小x个数
+ 结构体在此基础上再加两条：
	1. 每个成员的偏移量必须是该成员对齐要求的倍数（编译器在前面成员的后面**插填充字节**来满足）
	2. 结构体整体的对齐 = 最宽成员的对齐；总大小必须补齐到整体对齐的倍数（**尾部填充**）
### 堆栈上的对齐
+ 局部变量由编译器在栈帧里安排（[[_4#^04|SUB SP天然保持8字节对齐]]）
+ `malloc` 返回的指针保证满足最严格的基本对齐（8），这是 AAPCS 的规定，所以任何类型塞进 `malloc` 的内存都安全——**这是堆管理器要多付几个字节凑对齐的原因之一** ([[_5#^06|第 5 篇里“要 100 给 112”的一部分]])。
## 填充
+ 上面结构体处提到，使用尾部填充来实现结构体整体的对齐
+ 目的：保证结构体数组的每一个元素都满足对齐
+ 如果 `struct S`（最宽成员 4 字节）大小是 6，那么数组里第二个元素的起点就是“基址 + 6”——不是 4 的倍数，第二个元素的 `int` 成员立刻非对齐。所以必须补到 12
### 6字节的结构体算成12
+ 实验A解析
```text
偏移 0:  a        (char, 对齐 1, 放得下)
偏移 1:  ???      ← 填充 3 字节
偏移 4:  b        (int, 对齐 4 —— 偏移 4 是 4 的倍数, 才能放)
偏移 8:  c        (char, 对齐 1, 放得下)
偏移 9:  ???      ← 尾部填充 3 字节
总大小: 12
```
+ 6字节的数据，有3+3字节的填充
	+ 中间的填充：为了b的对齐，b要求4的倍数的偏移
	+ 尾部的填充：为了结构体整体的对齐，虽然c只占1字节，但是结构体最宽成员b是4字节，必须补到4的倍数12，**否则b就非对齐**
>我们知道硬件访问变量时要求它的起始地址必须是自身大小的整数倍，b的问题自然解决。那么为什么结构体需要整体的对齐呢？c的后面为什么需要填充呢？
>真正触发场景是**数组**
>假如定义`struct S arr[2]`，且不补尾部padding（9字节）
>`arr[0]`起始地址0没有问题，arr[0].a,arr[0.]b,arr[0].c（9字节）共都能正常访问
>arr[1].a落在10，也没问题；**但是，arr[b]就会落在11，这就是一个大问题**
### 优化
+ 换一个成员顺序:
```
struct T {
    int   b;      /* 偏移 0 */
    char  a;      /* 偏移 4 */
    char  c;      /* 偏移 5 */
};                /* 尾部补 2 → sizeof = 8 */
```
+ 实现0成本优化，减少了填充
+ 嵌入式编码规范（如 MISRA 相关实践）一般建议按对齐降序排列成员。
# 字节序
```text
uint32_t x = 0x12345678;   小端(STM32)         大端(网络字节序习惯)
地址低 → 高
0x20000000:         78  56  34  12              12  34  56  78
                    ↑                            ↑
                    最低字节在最低地址             最高字节在最低地址
```
+ **内存在两种设备之间搬运时**：串口发给另一块板、网线发给另一台机器、写进文件再读出来——**对方不知道你的摆法**，双方必须约定统一顺序
# 位域
+ `类型 成员名 : 位数`，编译器把多个小成员packing进“存储单元”
```c
struct Bits {
    uint8_t en   : 1;     /* 占 1 个位 */
    uint8_t mode : 3;     /* 占 3 个位 */
    uint8_t flag : 1;
    uint8_t rsv  : 3;
};                       /* 8 个位 = 1 个字节 */
```

|bit7|bit6|bit5|bit4|bit3|bit2|bit1|bit0|
|---|---|---|---|---|---|---|---|
|rsv2|rsv1|rsv0|flag|mode2|mode1|mode0|en|
>为什么位域不用手写掩码？
>编译器会自动生成掩码、移位、RWM逻辑，只需要xxx=bits.mode,无需自己维护掩码和移位逻辑
### 读改写
>底层本质：编译器**没有单独的 “位加载 / 位存储” 指令**，ARM/RISC-V/x86 只能读写整字节 / 整字。所有位域读写，都会展开成：**load → 移位 + and/or 掩码 → store**，也就是所谓的读改写（read-modify-write, RMW）
#### 读mode
+ uint8_t m=bits.mode
编译器逻辑：
1. LOAD：把整个uint8_t字节从内存/寄存器读到通用寄存器val
```
val =*(uint8_t *)&bits;
//&bits：取结构体bits的起始地址
//(uint8_t *)：将结构体指针强制转换位uint8_t*（指向单字节的指针）
```
2. 右移：把mode字段挪到最低位
```
val>>=1;
```
3. 与掩码0b111(0x7)，屏蔽掉高位无关bit
```
val&=0x7
```
4. 赋值给m
### 坑
1. 位在字节里的排布方向是实现定义[^2]的
	+ `en`占第0位还是第7位？->先声明的位域放在低位（LSB-first），还是高位（MSB-first）
2. 跨存储单元边界的分配是实现定义的
```c
struct Cross {
    uint8_t a : 6;
    uint8_t b : 5;     /* 6 + 5 = 11 > 8, 跨界了 */
};
```
+ b是紧贴着a继续排，还是整体挪到新单元？不同编译器答案不同
3. uint8_t作为位域类型本身有分歧
	+ `uint8_t en:1;` 是 GCC/AC6 友好扩展，**不是 C 标准强制**
	+ 标准里**原生推荐基础是 `int / unsigned int`**；`uint8_t / uint16_t / uint32_t` 属于**扩展支持**，不是强制要求所有编译器都认；
	+ 存储单元（storage unit）由实现决定：编译器决定把连续位域打包到多大的存储单元里（8/16/32bit）-->比如32bit,即使只定义8位，也会分配到32位的存储单元，即sizeof(xxx)=4，不是sizeof(x)=1

| 声明                 | 标准地位     | GCC ARM 行为   | sizeof | 适用场景                  |
| ------------------ | -------- | ------------ | ------ | --------------------- |
| `unsigned int x:N` | 标准规定合法   | 打包到 32bit 单元 | 4      | 标准可移植上限（但 bit 序依旧没保证） |
| `uint8_t x:N`      | 扩展支持，非强制 | 打包到 8bit 单元  | 1      | 单字节标志，GCC/AC6 嵌入式常用   |
| `uint32_t x:N`     | 扩展支持     | 打包到 32bit 单元 | 4      | 32 位外设寄存器（HAL 风格）     |
### 工程取舍
分层判断：
+ 只在本编译器、本工程的代码内部使用位域描述状态标志--没有跨界问题，可读性收益拉满（如协议解析的状态机标志）
+ 凡是描述“字节排布有外部约定”的东西（协议帧、寄存器）--位域排布是实现定义的，改用显式掩码+移位宏
补充一个细节：很多人误以为 ST HAL 里面大量位域。 区分两件东西：
- **CMSIS 底层寄存器定义（stm32f10x.h/core_cm4.h）：一律 Pos/Msk 宏，无位域**
- **HAL 高层结构体里，部分状态标志结构体用了位域** 刚好分层完全对齐： 
	✅ 高层软件状态、状态机标志、内部 flag（只在本工程、本编译器内部流转）→ HAL 敢用位域，拿可读性红利； 
	❌ 底层外设寄存器（和硬件硬件手册约定好固定 bit 布局，属于外部约定）→ CMSIS 底层坚决不用位域。
# packed
+ `packed` 的作用：**取消结构体成员之间、结构体末尾所有对齐填充字节，强制成员紧密连续排布，无视成员自身的自然对齐要求**。 它只修改**结构体内存布局**，**不改变 ABI 对指针类型的对齐契约** —— 这就是所有灾难的根源。
> AAPCS（ARM EABI）契约： 类型为 `uint32_t *` 的指针，**编译器有权默认它一定是 4 字节对齐**；`uint16_t *` 一定 2 字节对齐。这个约定和这个指针是不是指向 packed 结构体内部无关。

有些时候我们就是需要6字节的结构体--比如协议帧。串口发来的数据帧，头部1字节类型，4字节长度，1字节校验，物理排布由协议规定，一个填充字节都不能有，这时候使用packed：
```c
struct __attribute__((packed)) Frame {
    uint8_t  type;       /* 偏移 0，packed: 不填充 */
    uint32_t length;     /* 偏移 1 —— 注意！ */
    uint8_t  sum;
};                      /* sizeof == 6 */
//GCC/ARMCLANG 的 __attribute__((packed))、Keil AC5 的 `__packed` 关键字，效果相同：取消所有填充，成员紧挨着排。sizeof 从 12 变 6，offsetof(Frame, length) = 1。
```
## 安全场景
+ 直接通过带packed标记的结构体指针访问成员`fp->length`
+ 编译器知道 `fp` 是 `struct Frame*`，知道这个结构体是 packed，知道 length 在非对齐位置。 GCC / AC6 会**自动生成多字节加载序列（多次 LDRB 拼接）**，而不是一条 `LDR` 字加载。
> 重点：不是编译器总能救你，**取决于 CPU 内核是否支持非对齐访问**。
## 危险场景
+ 取出packed内部成员的地址，转成普通原生类型指针
```c
uint32_t bad_read(uint32_t *p) {
    return *p;
}
// 调用
bad_read(&fp->length);
```
+ 形参 `p` 是 `uint32_t *`，编译器依据 ABI 合同，生成对齐的单字加载指令 `LDR`。
>本质：**类型系统在这里断裂了**。packed 的约束只附着在外层结构体类型上，一旦单独取出内部成员的指针，packed 信息丢失，ABI 对齐假设恢复生效。
## 纪律
1. **packed 结构体成员，只通过本身的 packed 结构体指针访问**，不要剥离外层类型单独拿成员地址；
2. 如果要把成员传给外部函数：**先读到局部变量（拷贝出来），传值，不要传成员指针**
```c
// 正确 
uint32_t len = fp->length; //用多季节加载指令（LDRB四次），拼给len
process_len(len); 
// 禁止 
process_ptr(&fp->length);
```
3. 二进制协议解析，优先方案不是 packed 结构体强转；优先逐字节缓冲区 + CMSIS 式 `Pos/Msk` 移位提取。
## 风险方案
+ packed结构体强转buffer
```c
uint8_t rx_buf[6]; 
struct Frame *fp = (struct Frame *)rx_buf; // 非常常见写法
//但是不推荐，还是有风险
```
## 协议帧稳妥手法
```c
static uint32_t get_le32(const uint8_t *p)      /* 按小端拼 4 字节 */
{
    return (uint32_t)p[0]
         | ((uint32_t)p[1] << 8)
         | ((uint32_t)p[2] << 16)
         | ((uint32_t)p[3] << 24);
}

static void put_le32(uint8_t *p, uint32_t v)    /* 按小端拆 4 字节 */
{
    p[0] = (uint8_t)(v);
    p[1] = (uint8_t)(v >> 8);
    p[2] = (uint8_t)(v >> 16);
    p[3] = (uint8_t)(v >> 24);
}

void on_rx(const uint8_t *raw)
{
    uint8_t  type = raw[0];
    uint32_t len  = get_le32(raw + 1);     /* 对齐无关、字节序显式 */
    uint8_t  sum  = raw[5];
    ...
}
```
+ **结构体只做“值的容器”，字节流的进出永远走显式拼装函数**
>为什么不能就是传普通的结构体呢？
>因为普通结构体会插入padding，它的二进制布局和协议规定的帧格式对不上

[^1]:ABI:Application Binary Interface ，应用二进制接口
	ABI是编译完的机器码之间如何相互看懂、互相调用的底层协议
	嵌入式里常听到 **EABI（Embedded ABI）**，就是 ARM 嵌入式的 ABI 规范（ARMv7 EABI、AAPCS），规定 ARM 下参数怎么通过 R0~R3 传参、结构体对齐、位域顺序，写驱动、寄存器、内核模块时非常关键。
[^2]:实现定义：implenmentation-defined behaviour
