>堆是 SRAM 里除栈之外的另一块区域。它和栈物理上没有任何区别——都是普通的静态内存——区别全在管理方式上：栈由编译器在编译时就生成的 `PUSH`/`POP` 指令管理，堆由 C 库里一段运行时执行的软件代码管理。这段代码要记账、要对齐、要合并空闲块，而它的账本就写在给你用的内存隔壁。
>>注：为了让数字整齐，先做一个声明：本文的推演用一个教学模型——每块内存前面有 **8 字节的头部**，返回的指针 **8 字节对齐**。真实的 ARM 标准库和 newlib 细节略有出入（头部字段的组织方式、是否在块尾加边界标记），但“头部紧贴返回指针之前 + 8 字节对齐”这两点是共同的，推演结论不受影响。
# 现象
先做三个小实验
实验A：启动文件里默认 `Heap_Size EQU 0x00000200`（512 字节）。在 `main` 里申请一块 600 字节：
```c
char *p=(char*)malloc(600);//申请失败
```
实验B：堆里明明空着 264 字节（释放的 208 + 剩下的 56），申请 200 字节却失败
```c
char *p = (char *)malloc(100);   /* 成功 */
char *q = (char *)malloc(100);   /* 成功 */
char *r = (char *)malloc(100);   /* 成功 */
char *s = (char *)malloc(100);   /* 成功，四块共约 448 字节，预算 512 */
free(p);                          /* 释放第一块 */
free(r);                          /* 释放第三块 */
char *t = (char *)malloc(200);   /* NULL！ */
```
实验C：成功malloc一块内存后，越界写一个字节
```c
char *p = (char *)malloc(16);
p[16] = 0x55;                    /* 越界一个字节 */
free(p);                          /* 可能死在这，也可能死在很久之后 */
```
>三个现象分别对应堆的三个本质问题：**总量的硬边界**、**碎片**、**元数据的脆弱性**。下面按机制逐个展开
# 代价
+ 时间代价（非确定性）：malloc要遍历空闲链表做first-fit，free要检查左右邻居并可能合并。执行时间取决于堆的历史形状。堆干净时几微秒，**碎片化**后可能几十上百微秒。对 μs 级控制环路，这种抖动本身就是功能风险
+ 空间代价（元数据+内部碎片+外部碎片）：每个块前面有8字节头部；请求 100 字节实际占 112 字节（100+8 凑整到 8 的倍数）；`malloc(1)` 实际消耗 16 字节，开销是请求的 15 倍。分配 100 个 1 字节对象，消耗 1600 字节，真正"用上"的只有 100 字节。在 512 字节的堆上，内部碎片一项就能吃掉一半家底
+ 失败代价（NULL难处理+延迟爆炸）：`malloc` 失败返回 NULL，很多嵌入式代码不检查；更麻烦的是元数据损坏的**作案点与爆炸点分离**——`p[16]=0x55` 执行时毫无症状，几十层调用、几分钟之后才在 `free` 或 `malloc` 里炸开。调试器停在炸点时，看到的是一团被踩烂的链表，凶手早已执行完毕。
>malloc把空间管理、时间行为和失败处理的责任从编译期转移到了运行期，但是MCU 上最稀缺的恰恰是运行期的确定性。所以嵌入式很少用**malloc**
# 堆在物理上是什么
## 堆的大小
```asm
Heap_Size       EQU     0x00000200      ; 512 字节的预算
Area    HEAP, NOINIT, READWRITE, ALIGN=3
        SPACE   Heap_Size               ; HEAP 段，进 ZI
```
## 堆的物理边界
malloc不直接认识SRAM，也不认识启动文件。它和外界只有一个接口：`_sbrk`函数(Keil标准库下是同角色的一族函数)，语义是：“往上要 n 字节，成功返回新内存的起始地址，失败返回 -1”。
```c
//newlib版本的典型实现
extern char _end;        /* 链接脚本/链接器给出的符号：.bss 末尾 = 堆的起点 */
extern char _estack;     /* 链接器符号：SRAM 末尾 = 栈底方向的理论极限 */

static char *heap_end = 0;

char *_sbrk(int incr)
{
    char *prev;

    if (heap_end == 0)
        heap_end = &_end;        /* ① 第一次调用：堆从 .bss 末尾开始 */

    prev = heap_end;             /* ② 记住旧顶，这就是要返回给你的地址 */

    if (heap_end + incr > &_estack)   /* ③ 唯一的边界检查 */
        return (char *)-1;       /*    会撞到栈，拒绝 */

    heap_end += incr;            /* ④ 把堆顶指针往上挪 incr 字节 */
    return prev;                 /* ⑤ 返回旧顶 */
}
```
+ 堆的扩张就是挪char指针。它只把 `[旧顶, 旧顶+incr)` 这段地址划给你。这段内存里此前是什么（上电随机值），之后还是什么。
+ 实验A的 `malloc(600)` 失败路径正是这里：管理器发现空闲内存不够，调 `_sbrk(616)` 想扩地盘，`_sbrk` 一算 `heap_end + 616 > 边界`，返回 -1，`malloc` 于是返回 `NULL`。**你看到的 NULL，是这行 if 拒绝的结果**
>为什么是616？
>616=600+16，16字节：8字节头部+尾部边界标记8字节
# free list、元数据、碎片
## free list与一次完整的malloc
+ free list是malloc实现用来追踪”哪些内存当前可用“的数据结构。最简单的形式是一条单向链表，每个空闲块的开头存放指向下一个空闲块的指针。分配时从链表头开始找；释放时把块插回链表。
>以 `p = malloc(100)` 为例，采用教学模型：每块前 8 字节头部，返回指针 8 字节对齐。真实 ARM 标准库/newlib 的字段组织略有出入，但"头部紧贴返回指针之前 + 8 字节对齐"是共同的。
+ 第一次调用时空闲列表为空：
	1. 没有块能装下108字节（100+8--->对齐）
	2. 调 `_sbrk(512)`，拿到 `0x20000080`；->不同工程可能会变，不再是`0x20000800`
	3. 把这 512 字节包装成一个空闲块：`0x20000080` 处写头部 `[ size=504 | FREE ]`，`0x20000088` 起 504 字节可用-->8字节头部，504字节可用空间
	4. 请求 108 向上取整到 112，504 ≥ 112，**切块**：前半 112 字节头部改为 `[ size=104 | USED ]`，返回 `0x20000088`；后半在 `0x200000F0` 写新头部 `[ size=392 | FREE ]`，挂回链表；-->为什么是112，字节对齐
+ 连续4次malloc(100)后
```text
0x20000080  [ 104 | USED ]   p
0x200000F0  [ 104 | USED ]   q
0x20000160  [ 104 | USED ]   r
0x200001D0  [ 104 | USED ]   s
0x20000240  [  56 | FREE ]   ← 空闲链表上唯一的块
0x20000280  （预算上限）
```
## 元数据
元数据是“分配器为了管理内存而不得不记住的信息”：
+ 块大小（用于free时知道该归还多少）
+ 空闲/占用标志
+ 链表指针（空闲时）
+ 可选：边界标识，用于O(1)合并前后相邻块
这些信息附着在每个块的头部（或头部+尾部），对所有malloc块无条件征税
### 实验C
```text
X + 0    [ size=16 | USED ]     ← p 的头部
X + 8    p[0] ... p[15]         ← 你的 16 字节
X + 24   [ size=?? | FREE/USED ] ← 下一个块的头部第一个字节
X + 32   ...
```
p[16]落在X+24，正好是下一个块的size字段的最低字节，在p[16]写数据，就相当于修改了下一刻块的元数据：
1. size被改：如果下一个块空闲，size改大->块边界扩张，与后面的块重叠；size改小->下次从它切块时算出的剩余空间对不上。如果下一个块已经被占用，就损坏了这个块，炸在这个块free时
2. 标志位被篡改：空闲块被改成占用块；占用块被改成空闲块
3. free(p)可能当场炸掉：读 `p-8` 的头部拿 size=16；找右邻居 `p + 16 = X + 24`，读它的头部判断是否空闲、是否合并。右邻居头部已经被 `p[16]` 改坏，`free` 基于错误信息做合并决策——可能当场死在这。如果右邻居是 USED、不触发合并，`free(p)` 暂时没事，但坏头部留在堆里，等右邻居自己被 free 或后续 malloc 遍历到它时才炸
## 外部碎片VS内部碎片
+ 内部碎片：分配那一刻就产生、永远收不回来的浪费。
	+ 来源：8字节头部+凑整对齐
	+ malloc(100)拿到112字节，其中12字节永远用不到
+ 外部碎片是指**空闲内存总量足够，但没有一块连续的足够大的空闲区域**
	+ 比如实验B中3个洞共264字节，却装不下208字节的请求，因为没有连续的内存空间
+ 堆越小，碎片越致命
### 内存池
内存池是对碎片问题的直接回应：预先分配一大块连续内存，切成固定大小的块，用空闲列表管理借出和归还
```c
#define POOL_N     8          /* 块数 */
#define POOL_BLK   64         /* 每块字节数，等大 */->块大小固定

static uint8_t  pool[POOL_N][POOL_BLK];   /* 静态数组，.bss */
static uint8_t *free_list[POOL_N];//状态由“是否在free_list上”表达：块在链表就是空闲，不在就是占用，不需要每一个块都有FREE/USED标志
static int      free_top;

void pool_init(void)
{
    for (int i = 0; i < POOL_N; i++)
        free_list[free_top++] = pool[i];
}

void *pool_alloc(void)
{
    if (free_top == 0) return 0;          /* 满了：O(1)，时间确定 */
    return free_list[--free_top];         /* 弹出一块：O(1) */
}

void pool_free(void *blk)
{
    /* 实际实现要校验 blk 确实属于 pool，防错指针 */
    free_list[free_top++] = blk;          /* 压回去：O(1) */
    //不合并
    //free不需要反推，只需要把blk压回free_list数组
}
```
+ 碎片：所有块等大，分配永远整块进出，外部碎片按构造不可能存在；没有头部贴在数据前面，内部碎片为零。
+ 时间确定：alloc/free都是改一个下标，O(1)且常数极小，配合关中断或原子操作后中断里也能用
+ **元数据**：管理结构是独立的 `free_list` 数组，不在数据块隔壁——**越界写数据不会写坏账本**，实验 C 那种死法在池里不存在
>malloc必须有头部，因为它要同时支持：任意大小的块，任意顺序的释放，释放时合并邻居。free(p)只能拿到一个用户指针，它必须能从p反推出“这个块多大，是否空闲，左右邻居在哪”，所以管理信息只能紧贴在 `p` 之前（`p - 8`）
# 中断里的malloc/free
+ 中断里进制调用malloc/free
 + malloc/free修改的空间链表是一份全局共享数据，而它们的操作不是原子的。中断可以打断主循环正在执行的malloc/free，导致两个执行流同时编辑同一张链表
 ```text
 主循环正在执行 free(q)：
  步骤1: 读出 q 的右邻居 t 是空闲的
  步骤2: 准备合并 —— q->next = t->next        ← 执行到这一行之前
  ───────────── 中断到来 ─────────────
  中断里调用了 malloc(50)：
    遍历链表，从 t 上切走了 50 字节
    t 被改写成 [ 46 | USED ]，t 已不在空闲链表上
  ───────────── 中断返回 ─────────────
  步骤2 继续: q->next = t->next
 ```
 + 主循环还拿着中断前的信息准备合并，但是中断过后t已经不再是空闲块，这样就会把一个已经分配出去的块按空闲块处理，之后的某次malloc可能会把t再次发出去，损坏数据
